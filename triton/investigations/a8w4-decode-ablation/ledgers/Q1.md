# Q1 — the self-contained softmax top-k router

## The idea in one breath

Take the router's raw logits for a handful of decode tokens and, inside a single GPU workgroup, do the whole routing decision end to end — softmax, pick the top-k experts with a deterministic tie-break, read off their gate weights, optionally renormalize, and apply the routing scale — so routing never leaves the chip and never disagrees with the reference by a lane.

## Why this is a thing worth isolating

In an MoE decode step you have only M=1..4 tokens in flight (tiny-M), and before you can run any expert GEMM you must answer two questions per token: *which* experts and *how much* each contributes (the gate). That's a reduction over the expert dimension E — a softmax and a top-k — which is small, serial-ish, and awkward. The tempting shape is a separate "router" launch that writes IDs and gates to global memory, then a second kernel that reads them back. Q1 says: don't. For tiny-M the entire logits matrix (M x E) fits in registers of one wave32 workgroup, so route it there in one shot. The payoff is twofold: no extra kernel launch and no global round-trip on the critical path of a latency-bound decode, and — the part the study actually verifies — a *deterministic* result that matches a stable reference exactly on the integer expert IDs.

Sibling contrast: Q2 owns the biased-routing variant (sigmoid + correction-bias selection). Q1 deliberately drops the donor's optional bias path; Q1 selection is solely by full-row softmax score. The two cells split a single donor kernel along that seam.

## Worked example, end to end

Six experts, one token. Logits (deliberately containing a tie between experts 1 and 2):

`logits = [2.0, 1.0, 1.0, 0.5, -1.0, 0.0]`  (E=6, top_k=2)

Step 1 — softmax (max-subtracted, in FP32). Subtract the row max (2.0), exponentiate, divide by the sum:

`softmax = [0.466415, 0.171585, 0.171585, 0.104071, 0.023221, 0.063122]`

Notice experts 1 and 2 land on the *exact same* score 0.171585. That is the tie.

Step 2 — stable top-k selection (k=2, descending, ties go to the smaller expert ID):

- Rank 0: the largest score is expert 0 (0.466415). Select id 0.
- Rank 1: with expert 0 removed, the largest score is 0.171585 — shared by experts 1 and 2. The tie rule breaks toward the smaller ID, so select id 1, *not* id 2.

`selected ids = [0, 1]`  and their gates `= [0.466415, 0.171585]`

Step 3 — normalize the selected gates (divide by their sum 0.638000):

`normalized = [0.731059, 0.268941]`

Step 4 — apply the routing scale (say `routed_scaling_factor = 1.5`):

`gates = [1.096588, 0.403412]`

Final outputs for this token: IDs `[0, 1]` (int32), weights `[1.096588, 0.403412]` (fp32). If normalization were disabled the scale still applies — you'd get `[0.466415, 0.171585] * 1.5 = [0.699623, 0.257378]`. The scale is unconditional; normalization is the only optional step.

The kernel's own frozen tie test drives this to the extreme: four experts all at logit 3.0 with top_k=4 must come out as IDs `[0,1,2,3]` in exactly that order — pure tie, resolved entirely by ascending ID.

## The one-workgroup pipeline (pseudo-code)

```
load logits[M, E] into registers, cast to FP32   # masked; padding lanes = -inf
rmax   = rowmax(logits)                            # numerically-stable softmax
scores = exp(logits - rmax) / rowsum(exp(...))     # full-row softmax, FP32
cur    = scores  (with padding lanes forced to -inf)

for r in 0 .. top_k-1:                             # stable selection, one pass per rank
    vmax = rowmax(cur)                             # best remaining score
    id_r = rowmin( where(cur == vmax, col_index, E) )   # tie -> smallest column index
    gate_r = the score at column id_r
    record (id_r, gate_r) into slot r
    cur[:, id_r] = -inf                            # remove it so next rank moves on

if normalize: gates /= rowsum(gates)   (guard: sum==0 -> divide by 1)
gates *= routed_scaling_factor                     # always, even when unnormalized
store IDs (int32) and gates (fp32), masked to valid tokens only
```

Everything above is one grid program (`grid=(1,)`). No LDS, no scratch, no second launch — selection state lives in registers the whole time. `NUM_WARPS` is derived (1 warp for M<=2, else 4), not tuned.

## Why the two design choices matter

**Why stable ordering.** Top-k over floats is ambiguous whenever two experts tie, and ties are not exotic — they show up with symmetric initializations, saturated/extreme logits, and low-precision inputs (FP16/BF16 quantize distinct logits onto the same value). A naive `argmax`/`topk` can return whichever index the hardware reduction happened to visit first, which makes the result depend on lane scheduling and thus *nondeterministic across runs and divergent from the reference*. Q1 pins the rule — descending score, ties to the smaller expert ID — and implements it as "find the max, then take the min column index that achieves it." This is what lets the verifier compare IDs with *exact* integer equality rather than a tolerance, which is the only honest way to test a routing decision (a routing "close enough" is a wrong expert).

**Why one workgroup.** A separate router kernel means an extra dispatch and a global-memory write/read of the IDs and gates in the middle of a decode step that is already latency-bound at M=1..4. Folding it into one bounded workgroup keeps the whole decision register-resident and on the critical path exactly once. It also makes the semantic port a single, self-contained unit to reason about and verify, rather than a pipeline whose behavior depends on a synchronization boundary.

**Non-power-of-two padding.** GPU tile/layout shapes want powers of two, but E (and M, and top_k) are whatever the model says — e.g. E=13. The kernel rounds each up to the next power of two (EP=16 for E=13) for the register tile, then masks: padding columns are loaded as `-inf` and excluded from selection, so a padded lane can never be chosen as an expert and every emitted ID stays `< E`. Same masking guards the M and top_k padding on the stores, so only valid token rows are written.

## Honesty box

This is a **correctness-only** result. It ran under FFM (the functional model) on gfx1250, which has no meaningful timing — so the "avoids a launch / avoids a global round-trip" argument is a design rationale, *not* a measured speedup. What is actually established: for the tested contract (M={1,4}, top_k={1,4}, E={8,13}, FP16/BF16/FP32, normalize on/off, four routing scales), the one-workgroup kernel reproduces a stable reference with exact expert IDs and FP32 gate error at most ~6e-8, including deliberate ties, extreme logits, and non-power-of-two E. Performance, non-finite inputs, real-silicon behavior, and downstream fusion are out of Q1's scope. The only architecture change from the gfx950 donor is distributing the expert row over 32 lanes (wave32) instead of 64; the bias-based routing path was intentionally dropped and belongs to Q2.

- Before Q1, H0 contains only the grouped A8W4 GEMM and consumes routing metadata produced outside its owned source. It owns no router program.
- After Q1, grid program 0 owns the complete bounded `M x E` logits matrix, performs every row reduction and stable selection in registers, and stores the complete `M x top_k` ID/gate outputs. No second program or launch participates.
