# R5 — output-owned top-k down projection

## The idea in one breath

Flip who owns the work in the MoE down-projection: instead of one program computing one expert's contribution and dumping a row for someone else to combine later, one program owns a whole *output token* — it loops that token's top-k experts itself, folds `gate * expert_out` into a single FP32 register accumulator, and writes the finished token row exactly once. The top-k combine disappears into the compute. This is the W2 pattern that R7/I1/I2 reuse; it contrasts with G7's atomic combine (below).

## The ownership flip

Both R1 (parent) and R5 do the same math — a per-route A8W4 wave-GEMV down projection — but they slice the grid on different axes, and that changes everything downstream.

R1 owns a **(route, N tile)**. Each program computes one expert's projection for one token slot and *stores it*. Nobody has combined anything yet: the top-k sum still has to happen in a second pass (weight-multiply + reduce over the `top_k` route rows per token), which needs a materialized `[M*top_k, N]` route buffer read back from global memory.

R5 owns a **(token, N tile)**. One program walks all `top_k` slots for its token, and the combine is just `+=` on a register. No route buffer is ever born, so nothing needs to be read back and reduced.

```
  R1: route-owned  ── emit rows, combine LATER
  ────────────────────────────────────────────────
  prog(route=t0k0) ─► out0 ─┐
  prog(route=t0k1) ─► out1 ─┤   [M*top_k, N] route buffer
  prog(route=t0k2) ─► out2 ─┤   in GLOBAL memory
  prog(route=t0k3) ─► out3 ─┘        │
                                     ▼
                          ── separate combine pass ──
                          token0 = Σ gate_s * out_s   (reads 4 rows back)


  R5: token-owned  ── combine IN PLACE, store ONCE
  ────────────────────────────────────────────────
  prog(token=t0) ─┐  slot0: acc += gate0 * expert0_out
                  │  slot1: acc += gate1 * expert1_out    (acc lives in
                  │  slot2: acc += gate2 * expert2_out     FP32 registers)
                  │  slot3: acc += gate3 * expert3_out
                  └► ONE store: out[token0] = acc
```

The accumulator folds the whole top-k sum as it goes — `gate0*out0 + gate1*out1 + gate2*out2 + gate3*out3` — and only the finished total ever touches global memory.

## The R5 loop, in pseudo-code

```
token, n_tile   = decode(program_id)          # (token, output tile) ownership
acc[BLOCK_N]    = 0.0   (FP32, in registers)  # the token's running output

for slot in 0 .. TOP_K-1:                      # statically unrolled
    expert = route_ids[token, slot] - expert_start
    gate   = routing_weights[token, slot]      # FP32 gate for this slot
    route  = token * TOP_K + slot              # which prebuilt A8 row to read

    route_acc[BLOCK_N] = 0.0
    for k0 in 0 .. K step BLOCK_K:             # within-wave K reduction
        x = dequant(intermediate[route, k0:], intermediate_scale[route])  # A8 -> FP32
        w = scaled_upcast(packed_W2[expert, ...])                          # W4 -> BF16
        route_acc += sum(w * x, axis=K)        # gl.sum over the wave

    route_acc += bias[expert]                  # optional, before weighting
    acc += gate * route_acc                    # <-- combine folded in, FP32

store(out[token, n_tile], acc)                 # exactly ONE store
```

Everything the token needs — the per-slot expert, its gate, its A8 activation row, its packed W2 weights — is fetched inside the loop and reduced into one register accumulator. The gate multiply happens in FP32 right before the fold, so the top-k sum is accumulated at full precision in slot order.

## Why it matters

The point isn't the arithmetic (identical to R1) — it's what the ownership choice *eliminates*. Because one program owns the entire token, the combine is register-local, so R5 needs **no route/combine buffer** and **no atomics**:

- **vs. R1's deferred combine:** R1 must write `M*top_k` route rows to global memory and run a second reduction kernel (the negative-space reference `aiter/.../moe/reduce.py`, which loads routed rows and sums them). R5 removes that entire buffer and pass — the routed intermediate results never leave registers.
- **vs. G7's atomic combine:** another way to fold top-k without a separate pass is to have every route program atomically add its weighted output into a shared token row. That keeps route-level ownership and pays for cross-program atomics + read-modify-write contention. R5 sidesteps both: since a single owner accumulates all slots, there is nothing to atomically merge — just one clean, contention-free `global_store`. G7 separately owns the atomic-combine alternative.

So the three shapes of the same combine are: R1 = buffer + second pass; G7 = atomics into shared output; R5 = register accumulate + one store. R5 is cleanest when a single wave can afford to own the whole token (tiny-M decode, few tokens, small top-k).

## Honest scope

FFM validates **correctness only — no timing**. R5 was proven numerically equivalent to R1's math component-wise (route projection, weighted projection, running partial, final output all matched an independent host reference within the pinned A8W4 tolerance), and the *structural* claims were checked in the compiled artifact: production specializations emit exactly one `tt.store` / one `global_store_b32`, allocate zero shared and zero global-scratch bytes, and contain no atomic and no route/combine buffer symbol. What remains unknown is whether output ownership is *faster* than route ownership for any real decode shape — occupancy, register pressure, and the output-owned-vs-route-owned crossover need real hardware and are outside this cell.
