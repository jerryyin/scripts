# G3 — Decode routing once, then walk three N tiles

## The idea in one breath

Instead of launching a separate workgroup for every (M-block, N-tile) output tile — each of which independently re-derives which expert it serves and where that expert's rows live — one workgroup does that routing decode a single time, then loops over three neighboring N tiles in place, reusing all the routing and descriptor setup across them.

## The picture

In an MoE decode GEMM the output is a grid of tiles: one axis is the padded M block (which expert, which rows), the other is the N tile (which slice of the output columns / weight columns). The baseline assigns one program per output tile, so along the N axis three adjacent tiles are three fully independent programs — and each one repeats the same expensive "who am I" bookkeeping before it touches any math.

```
BEFORE (baseline H0): one program per output tile
                                                          per-program work:
  prog(m, n=0):  [decode route][build descs] -> [K pipeline -> store]   route decode #1
  prog(m, n=1):  [decode route][build descs] -> [K pipeline -> store]   route decode #2  (redundant)
  prog(m, n=2):  [decode route][build descs] -> [K pipeline -> store]   route decode #3  (redundant)
                  \______ same for all 3 ______/
                  expert id, start_m, off_m, off_k, X/gather desc are IDENTICAL across n

AFTER (G3): one program per group of 3 N tiles
  prog(m, group=0):
      [decode route][build X desc]      <-- done ONCE
        |
        +-- n_iter 0 (tile n=0): [K pipeline -> bias/act -> store]
        +-- n_iter 1 (tile n=1): [K pipeline -> bias/act -> store]
        +-- n_iter 2 (tile n=2): [K pipeline -> bias/act -> store]
              ^ only the N-dependent offsets (W, W-scale, bias, output col) advance
```

The amortized work is everything that depends only on the M block and the expert, not on N: computing the program's expert id, the ragged-M start row, the K-tail offset, the gather index vector, and the X input tensor descriptor. In the baseline that whole prologue runs three times for three neighboring column tiles; in G3 it runs once and is shared. What is deliberately *not* shared: X is still re-loaded from global into LDS for each N tile's K pipeline, and W / W-scale global traffic is unchanged. So this isolates the setup-amortization idea cleanly, without also claiming data residency across tiles.

Why exactly three? It is a fixed fusion factor copied verbatim from the AITER donor kernel — a hand-tuned constant, not a derived one. The logical N grid is contracted by three (`ceil(grid_n / 3)`), each surviving workgroup owns N-tiles `3g, 3g+1, 3g+2`, and a runtime guard lets the last group exit early after one or two tiles when `grid_n` is not a multiple of three.

## The persistent loop, in pseudo-code

```
pid = program_id()
persistent_grid_n = ceil(grid_n / 3)
if pid >= unpadded_m * persistent_grid_n: return      # contract the oversized launch grid

pid_m, pid_n_group = decode_pids(pid, persistent_grid_n)
first_pid_n = pid_n_group * 3

# ---- decoded ONCE for the whole group ----
expert_id, start_m, off_m, off_k = compute_offsets(pid_m)   # routing
X_desc = build_x_descriptor(expert_id, start_m, off_m)      # activation side
W_base_offset = first_pid_n * BLOCK_N                       # column of tile group start
out_smem = alloc_output_lds()                              # one buffer, reused

# ---- looped over the 3 consecutive N tiles ----
for n_iter in static_range(3):
    pid_n = first_pid_n + n_iter
    if pid_n >= grid_n: return                             # tail guard
    acc = k_pipeline(loop_k, n_iter)   # n_iter shifts W / W-scale column offsets only
    acc += bias[pid_n]                 # per-tile numeric boundary is unchanged
    out = convert(activation(acc))
    store_or_scatter(out, column = pid_n)
```

The single change threaded into the inner K pipeline is an `n_iter` argument that adds `n_iter * BLOCK_N` to the W column offset (and the matching offset to the W-scale load); everything else in the numeric path — scaled-WMMA, FP32 accumulation, bias, dtype conversion, TDM store/scatter — is byte-for-byte the baseline, just executed three times.

## Worked example

Take `grid_n = 4` (case G3-C3, N=400, BLOCK_N=128 → 4 column tiles per M block). Baseline launches 4 programs per M block, each re-decoding routing. G3 contracts to `ceil(4/3) = 2` logical groups per M block:

- Group g=0 → `first_pid_n = 0`, walks N-tiles `0, 1, 2` (W column offsets `0, 128, 256`), decoding routing once for all three.
- Group g=1 → `first_pid_n = 3`, walks N-tiles `3, 4, 5`; tile 3 is valid, tiles 4 and 5 hit `pid_n >= grid_n` and the workgroup returns. So the last group runs a full-group-plus-tail pattern: 3 tiles then 1 tile.

For the common `grid_n = 2` cases, one group covers both tiles and the third slot exits immediately — still one routing decode instead of two.

## Why it might matter (and the honest caveat)

The bet is that at tiny M (decode, M=1..4) the per-tile numeric work is small, so fixed per-program overhead — routing decode, descriptor construction, kernel-launch/dispatch cost, prologue instructions — is a meaningful fraction of runtime. Folding three tiles into one program cuts that overhead roughly threefold along the N axis and cuts the launched workgroup count by ~3x, which can also improve occupancy scheduling. That is the mechanism AITER's production kernel is exploiting.

The caveat, stated plainly: this cell was verified under **FFM, which models correctness only and produces no timing**. All 25 cases match the reference bit-exactly, and the compiled TTGIR confirms one routing decode / one X descriptor feeding three K loops and three stores. But whether the amortization actually pays off — the crossover point, cache-residency effects, and the right fusion factor — is unknown until it runs on real B0 hardware. G3 makes no performance claim; it proves the idea is *correct* and structurally does what it says. This contrasts with the sibling cells that change math or layout rather than ownership: G2's all-N warp layout, G4's packed schedule, and G5's weight preshuffle are excluded here by design (see Source diff classification).
