# R8 — output-owned scaled-WMMA register lookahead

## The idea in one breath

Before the matrix engine chews on the current K-tile pair, already fire off the global loads for the *next* pair — classic register double-buffering, so slow HBM reads overlap with fast WMMA math instead of stalling in front of it.

## Where it sits

R7 (its parent, `k14_output_owned_topk_scaled_mfma.py`) walks the K dimension one tile at a time: load a 128-element fragment, feed it to a scaled WMMA, repeat. Each iteration pays the full round-trip to global memory *before* the matrix engine can start. On a tiny-M decode kernel, where there is almost no other work to hide behind, that load latency sits on the critical path. R8 keeps *everything* about R7 identical — same output ownership, same duplicated-16-row layout, same `wmma_scaled` arithmetic, same top-k order — and changes only *when* the loads are issued relative to the compute.

## No prefetch (R7) vs lookahead (R8)

R7 — serial, load blocks compute:

```
load p0 ──▶ [WMMA p0] ──▶ load p1 ──▶ [WMMA p1] ──▶ load p2 ──▶ [WMMA p2] ...
            ^stall while                ^stall while
             p0 arrives                  p1 arrives
```

R8 — lookahead, the next load runs *underneath* the current compute:

```
load p0
        ├─ load p1 ─┐
        [WMMA p0]   │   <- p1's HBM read overlaps p0's matrix math
                    ├─ load p2 ─┐
        [WMMA p1]   │           │
                    ├─ load p3 ─┐
        [WMMA p2]   │           │
                    ...
        [WMMA p_last]           <- operands already resident, no wait
```

The point: in R8 every WMMA (except the very first) finds its operands *already in registers*, because the load that fetched them was launched a full pair earlier and ran concurrently with the previous pair's matrix work. Latency is paid once at the prologue instead of once per tile. (A "pair" is two 128-element K fragments — the granularity R8 double-buffers at, matching the precision-matched donor.)

## The prefetch loop, in pseudo-code

```
preload current_pair = (load frag0, load frag1)        # prologue: eat latency once

for pair i in 0 .. (last complete pair - 1):
    next_pair = (load frag[2i+2], load frag[2i+3])     # issue NEXT pair's loads...
    acc = wmma(acc, current_pair.even)                 # ...then consume CURRENT pair
    acc = wmma(acc, current_pair.odd)                  #    (loads run underneath)
    current_pair = next_pair                           # promote

acc = wmma(acc, current_pair.even)                     # drain the last prefetched pair
acc = wmma(acc, current_pair.odd)

if K has an odd leftover fragment:                     # epilogue for odd fragment count
    tail = load frag[last]                             # e.g. K=384 -> 3 fragments
    acc = wmma(acc, tail)                              # consumed serially, no partner
```

The source-order invariant that makes it "lookahead" and not just "reordered code": within the loop body, the **next** pair's `load` statements appear textually *before* the WMMA that consumes the current pair, and the promote happens *after*. K=128 is rejected up front — a single fragment can't form a pair, and silently falling back to R7's serial schedule would erase the only idea being tested.

## Why it matters

Matrix-engine kernels are usually memory-latency-bound at the edges of the K loop, not compute-bound. Prefetching is the cheapest, most portable latency-hiding trick there is: no LDS, no scratch, no extra buffers beyond a second set of registers — you just reorder issue so the load-warp and the matrix pipe are busy at the same time. R8 spends exactly that (a doubled register live-set for the in-flight pair) and nothing else.

## The crucial honest caveat

**The source expresses the pipeline. Whether the compiler *keeps* it is unproven.** This is the whole teaching point, and the ledger is candid about it.

R8 was validated under **FFM — the functional model, which checks correctness only and has no notion of timing.** Every captured tensor and the production output are *bitwise* equal to R7 across K=256/384/512, so the reordering is provably a no-op on the math. But bitwise equality says nothing about overlap.

When the ledger inspected the lowered TTGIR at K=512, it found the compiler had **hoisted all 12 operand loads for a route ahead of that route's first WMMA** — after constexpr/static unrolling, the pairwise "load-next-then-compute" shape had dissolved into "load everything, then compute everything." That ordering is *consistent* with the source dependency graph, but it is **not evidence that a pairwise software pipeline survived to codegen.** The compiler may already hoist loads on its own regardless of how the source is written, which would make the hand-written lookahead a no-op at the level that matters for performance.

So the correct reading is layered:

- **Source level:** the intended pipeline is present and correct — verified.
- **Numerics:** bitwise-identical to R7 — verified.
- **Codegen level:** the pairwise overlap could **not** be shown to survive lowering at K=512 — *open question*.
- **Hardware timing / actual load-WMMA overlap:** unmeasured by construction (FFM has no timer). No speed or overlap claim is made.

The K=384 case is a partial exception worth noting: its TTGIR *did* retain the donor's remainder distinction (six pair loads before the first WMMA, exactly three odd-fragment loads wedged between the pair's last WMMA and the final tail WMMA), so the odd-epilogue structure is at least visible there.

### Failure isolation during validation

- The first odd-fragment full attempt expected three WMMAs but generated five. Cause: a mechanical port error — an element-unit `range(0, K - 2*BLOCK_K, 2*BLOCK_K)` still executes once for K=384, loading a nonexistent fourth fragment and duplicating the odd fragment. Fix: mechanically match the donor by rounding to `paired_k_end` before deriving the steady-loop bound.
- The first compile after that fix rejected `paired_k_end` because a `gl.constexpr` declared inside `gl.static_range(TOP_K)` is redeclared for every unrolled slot. Hoisting that K-only constexpr outside top-k fixed compiler scope without changing the schedule.
- The next odd-fragment attempt generated the correct three WMMAs, but a harness assertion demanded all nine operand loads before the first WMMA. That contradicted the donor's serial odd epilogue. The audit was narrowed to six pair loads before pair compute plus exactly three remainder loads before the final WMMA.
