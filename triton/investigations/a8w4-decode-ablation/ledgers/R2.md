# R2 — one activation stream, two projections (fused gate/up + SwiGLU)

## The idea in one breath

An MoE FFN's first matmul secretly does two projections of the *same* activation — a gate and an up — so read the activation X once, fan it into two register accumulators at once, and finish with the fused `SiLU(gate) * up`, instead of running two independent GEMVs that each re-stream X.

## Why this idea exists

In the R-series each wave already owns one `(route, N tile)` and streams the selected expert's 4-bit weights while reducing K as a GEMV in registers — that is the parent, R1. But the real W1 layer isn't one projection: it produces a **gate** vector and an **up** vector, then combines them with SwiGLU: `out = SiLU(gate) * up`. The naive way to reach that from R1 is to run R1 twice — once for gate columns, once for up columns — and both passes hit the exact same activation row of X. R2's insight is that X is the shared operand: the two projections differ only in *which weight columns* they multiply, so the activation load can be hoisted out and reused. The intermediate-precision siblings build on this same fused body: R3 owns the later BF16 gate/up-or-intermediate rounding boundary and R4 owns its static-FP8 sibling boundary; R2 keeps everything FP32.

## The picture

R1-twice (what R2 replaces): each pass re-reads the whole X stream.

```
   pass 1 (gate):   X ──► [gate GEMV] ──► gate            X read #1
   pass 2 (up):     X ──► [up   GEMV] ──► up              X read #2   ← redundant
                    then, separately:  SiLU(gate) * up
```

R2 (one stream, dual accumulate): X is read once per K-tile and fanned out.

```
                       ┌──────────► (× gate weights) ─► gate_acc ┐
   for each K tile:    │                                          │
     X_tile ──(load)───┤                                          ├─► SiLU(gate)*up ─► out
                       │                                          │
                       └──────────► (× up   weights) ─► up_acc  ──┘
                    ↑ ONE load                     ↑ TWO accumulators, both register-resident
```

The wave still owns exactly one `(route, N tile)`; nothing about routing, K-reduction, or the no-grouping / no-LDS / no-WMMA character changes. R2 adds precisely one extra weight+scale+bias stream (the "up" half) and one extra FP32 accumulator.

## The fused K loop, in pseudo-code

```
gate_acc = 0        # FP32, register-resident, [BLOCK_N]
up_acc   = 0        # FP32, register-resident, [BLOCK_N]

for k_tile in K:
    x = load(X[route_row, k_tile]) * activation_scale      # <-- ONE load, shared

    gate_w = scaled_upcast(load(W_gate[expert, k_tile]))   # 4-bit -> bf16
    up_w   = scaled_upcast(load(W_up  [expert, k_tile]))   # gate/up are the two
                                                           # halves of one packed [K/2, 2N] tensor:
                                                           #   columns [0,N) = gate, [N,2N) = up

    gate_acc += reduce_K(gate_w * x)                       # both reductions consume
    up_acc   += reduce_K(up_w   * x)                       # the SAME x

gate_acc += gate_bias
up_acc   += up_bias

# SwiGLU, in FP32:
silu_gate = gate_acc * sigmoid(gate_acc)   #  = gate * 1/(1+exp(-gate))
out       = silu_gate * up_acc
store(out)                                 # one final FP32 route row
```

Contrast the R1 loop body, which has a single `acc`, a single weight stream, and stores that projection directly — no activation, no second accumulator. R2 is that loop with the activation-load lifted to the top and the multiply/reduce duplicated over two weight halves.

## Why it matters

- **Activation reuse.** The tiny-M decode regime is memory/latency-bound, not FLOP-bound: a wave spends its time issuing loads. Reading X once instead of twice halves the activation traffic for the W1 layer and removes a redundant pass over the same K stream. The weight traffic is unavoidably doubled (gate and up are genuinely different weights), but the activation is genuinely shared, and that's the part R2 recovers.
- **Register-resident dual accumulate.** Both `gate_acc` and `up_acc` live in registers across the whole K loop; the two dot products interleave in the same wave with no LDS, no scratch, no matrix unit. The activation `x` is loaded into registers and immediately feeds both multiplies while it's hot.
- **The fusion is free at the seam.** Because both projections finish in registers in the same program, SwiGLU (`SiLU(gate) * up`) is just a handful of FP32 ops on values already present — no round-trip to global memory to recombine gate and up, and no separate elementwise kernel.

## Honest scope

This is a **correctness-only** result under FFM (the functional model has no timing). The reuse and traffic-reduction argument above is the *motivation* for the idea; FFM cannot measure it. What FFM does confirm is that the fused dual-accumulate + SwiGLU is numerically sound: gate and up match the FP32 reference exactly, and the fused final output stays within a max absolute error of about `2.98e-8` on the independent smoke — i.e. FP32 round-off, not an algorithmic discrepancy. Whether one-stream-two-accumulators actually beats two R1 passes on real hardware (occupancy, register pressure, cache behavior) is out of scope here and left to later timing work.
