# H0 — The Frozen Baseline (PR #154 parameterized decode; the mental model every other card forks from)

## The idea in one breath

H0 is not a new trick — it is one grouped **A8W4 MoE-decode GEMM** frozen exactly as PR #154 wrote it, with every tuning knob turned into a test-selectable dial, so every later ablation is measured as a delta against this one reference kernel. Read this card once and you'll understand what *all* the other cards are modifying.

## What problem this kernel solves

MoE decode is the autoregressive step of a Mixture-of-Experts model: you have a tiny batch of tokens (`M = 1..4`, "tiny-M"), a router already picked which expert each token goes to, and you must run each token through *its own* expert's weight matrix. So this is not one big matmul — it's many skinny `(few tokens) × (expert weights)` matmuls, one per expert, glued into a single kernel launch. The weights are 4-bit (`W4`), the activations are 8-bit (`A8`), and both carry microscales that must be applied during the dot product.

The whole kernel is: **for my assigned (expert, token-tile, output-column-tile), stream the K dimension through fast memory, do a scaled low-precision matmul, add bias, and write my rows back to where the router wants them.**

## Data-flow pipeline (real shapes: the C5 case, M=2 N=256 K=1024, BLOCK 128/128/256)

```
 routing metadata            X (tokens)  W (expert weights, 4-bit)   scales
 XSliceSizes/Offs            [M,K] E4M3  [E,K,N] packed E2M1         UE8M0
 XBlockSchedule                  |            |                        |
        |                        |            |                        |
        v                        |            |                        |
 [1] RAGGED BLOCK SCHEDULE       |            |                        |
   flatten every expert's        |            |                        |
   token rows into padded        |            |                        |
   BLOCK_M tiles; grid = 2×2     |            |                        |
        |                        |            |                        |
        v                        v            v                        v
 [3] TDM engine streams K in BLOCK_K=256 chunks into LDS (double/N-buffered)
        x_buffer[NUM_BUFFERS,128,256]   w_buffer[...]   x/w scale buffers
        |                        |            |                        |
        +----------- K-reduction loop (NUM_BUFFERS-deep software pipeline) --+
        |            issue_global_loads -> async_wait -> issue_local_loads   |
        v                                                                    |
 [4] SCALED WMMA:  acc[128,128] += wmma_scaled(x, sx, E4M3, w, sw, E2M1) ----+
        |   accumulate in FP32 across all K chunks
        v
 [5] acc += bias (FP32) -> cast to output dtype (E4M3/E5M2)
        v
 [6] stage tile in LDS, then TDM async_scatter rows to router-chosen output rows
        Y [writeback_size, N]   (or async_store for the non-scatter path)
```

(Step [2]: one program = one `(expert_id, padded M-tile off_m, N-tile pid_n)`; `compute_pids` / `compute_offsets` resolve which is mine.)

## Vocabulary every future card assumes

- **Expert grouping / ragged block schedule.** The router assigned a *variable* number of tokens to each of the ~10 experts (`XSliceSizes`). Rather than launch per-expert, the host flattens all experts' token rows into a single list of fixed-size `BLOCK_M` tiles and records, per tile, which expert it belongs to (`XBlockSchedule`, `XBlockOffs`). "Ragged" = the M dimension has uneven per-expert lengths. `grid_m` in the evidence is the *number of these tiles*, which is why e.g. M=16 tokens over experts yields 8–10 blocks, not one.
- **Padded M tile.** Each block is `BLOCK_M` rows even when the expert only has 3 real tokens; the tail rows are padding, masked on load and on writeback (`off_m + idx < eM`). This is why `BLOCK_M=16` and `BLOCK_M=256` both work for M=1 — the tile size is a tuning choice, not the token count.
- **Program ownership.** One `program_id` → `compute_pids` → `(pid_m, pid_n)` → `compute_offsets` → `(expert_id, off_m, off_k_x)`. That one program owns exactly one (expert-weight-block, padded M-tile, N-column-tile) and runs the whole K-loop for it.
- **Gather vs scatter.** *Gather* = the input rows I need are scattered in X, so I read them through a `GatherIndx` (`async_gather`). *Scatter* = I compute a dense output tile and write each row to its router-chosen destination via `WriteBackIndx` (`async_scatter`). H0 exercises both; note (see boundaries below) that gather has a hard constraint with `BLOCK_K=128`.
- **TDM (Tensor Data Movement).** The gfx1250 async DMA engine. `make_tensor_descriptor` describes a tiled view of a global tensor; `async_load` / `async_gather` / `async_store` / `async_scatter` move blocks between HBM and LDS without occupying the ALUs. `async_wait(n)` blocks until ≤ n outstanding.
- **LDS staging.** Shared memory. `x_buffer`/`w_buffer` are `[NUM_BUFFERS, ...]` ring buffers: TDM fills buffer `i%NUM_BUFFERS` while WMMA consumes an earlier one — that is the software pipeline (`pipeline()` prologue + steady state).
- **Scaled WMMA.** The matrix core op. `wmma_scaled(x, scale_x, "e4m3", w, scale_w, "e2m1", acc)` multiplies low-precision operands and applies their microscales inside the instruction, accumulating in FP32. Instruction K-width is 64 for packed 4-bit vs 128 unpacked — hence the layout machinery.
- **E2M1 / UE8M0.** `E2M1` = 4-bit float weights (1 sign, 2 exp, 1 mantissa), two packed per byte (`DIV_FACTOR_W=2`). `UE8M0` = 8-bit unsigned power-of-two microscale, one per **group of 32** elements (`SCALE_BLOCK=32`). Dequant value ≈ `E2M1_value * 2^(scale-127)`.
- **The tuning axes** (the dials H0 froze but left selectable — each later card perturbs one): `BLOCK_M {16,64,128,256}`, `BLOCK_N {64,128,256}`, `BLOCK_K {128,256}`, `NUM_WARPS {4,8}`, `NUM_BUFFERS {2,3,4}`, movement `{gather,scatter}`, activation dtype `{E4M3,E5M2}`, and scale layout `{STRIDED, PRESHUFFLED}`. Frozen-off (not dialed in H0): `SCHEDULE='baseline'`, `PINGPONG=False`, `L2_PREFETCH_DISTANCE=-1`, `PARTIAL_TDM=False`, `RESOLVE_PARTITION_CONFLICTS=False`, `TDM_SPLIT=False`, `SPLIT_K=1`, `RAGGED_DIMENSION='M'`, `NUM_SUBTILES=(1,1,1)`.

## The kernel body as pseudo-code

```python
pid = program_id()
skip if pid is a padding tile
expert_id, off_m, off_k_x, pid_n = resolve_from_schedule(pid)   # who am I?

x_desc, w_desc, sx_desc, sw_desc = make_tdm_descriptors(expert_id, off_m, pid_n)

acc = zeros([BLOCK_M, BLOCK_N], f32)
for k_chunk in range(cdiv(K, BLOCK_K)):          # software-pipelined, NUM_BUFFERS deep
    tdm.async_load / async_gather  x, w, scales -> LDS[k_chunk % NUM_BUFFERS]
    async_wait(NUM_BUFFERS - 1)
    x, w, sx, sw = load_from_LDS(k_chunk)
    acc = wmma_scaled(x, sx, E4M3, w, sw, E2M1, acc)   # FP32 accumulate

acc += bias                                       # FP32
out = acc.to(E4M3_or_E5M2)                         # one-byte output
if scatter: tdm.async_scatter(out -> Y[WriteBackIndx])
else:       tdm.async_store  (out -> Y[off_m ...])
```

## Worked micro-example (case C1: M=1, N=256, K=512, scatter, BLOCK 16/64/128)

1. One token, routed to expert `e`. Schedule produces `grid_m=1` block (16 padded rows, 1 real), `grid_n = 256/64 = 4` column tiles → 4 programs total (grid `1×4`).
2. Program `pid_n=2` owns expert `e`'s weight columns 128–191. It loops K in `512/128 = 4` chunks, TDM-streaming X `[16,128]` and packed W into LDS with `NUM_BUFFERS=2` double buffering.
3. Each chunk: `wmma_scaled` applies UE8M0 microscales (one per 32 K-elements) to E4M3 activations and E2M1 weights, accumulating `acc[16,64]` in FP32.
4. Add bias, cast to E4M3, then `async_scatter` writes the single valid row to `Y[WriteBackIndx[0]]`; the 15 padding rows are masked out.
5. Reference is the dequantized `matmul_torch`; after the source's one-byte rounding boundary the error is exactly 0.

## Two boundaries H0 pinned down (later cards inherit these)

- **Non-ragged decode is rejected.** Calling decode without M-ragged metadata raises exactly `decode kernel only supports M-ragged (MoE) gemms`. Decode is MoE-only by contract.
- **gather + BLOCK_K=128 does not compile.** The frozen config picks `PAD_INTERVAL_X=256`, and TDM gather requires that interval to divide the innermost block dim; 256 ∤ 128. This is a real layout/descriptor constraint, not loosenable in a harness — the two planned gather cases were legally swapped to scatter, keeping every tuning-axis value covered. Remember this when a later card wants gather at small BLOCK_K.
