# R7 — Output-owned top-k with scaled-WMMA reduction

## The idea in one breath

Keep R5's clean deal — one program owns one (token, output-tile), loops that token's top-k experts, and writes the answer exactly once — but stop doing each expert's down-projection with a hand-rolled vector dot; instead feed the FP8 activation row and the packed-FP4 expert weights straight into the gfx1250 matrix core (scaled WMMA), one expert at a time.

## Why this cell exists

A8W4 MoE decode is the tiny-M regime: at decode you have essentially one token per expert, so the "GEMM" for each expert is really a GEMV — a single activation row times a weight matrix. Two independent design choices govern how you run that:

- **Ownership (who writes what):** does a program own a *route* (one token-expert pair) and emit a partial result that someone else must combine, or does it own the *output* (a token's final row) and fold all its experts internally, storing once?
- **Reduction engine (how the dot is computed):** do you sum the products yourself across the wave (a vector GEMV, `gl.sum` over K), or do you hand the multiply-accumulate to the matrix core?

R7 is simply the corner where both good choices meet: output-owned *and* matrix-core.

## The 2x2 that places the family

|                          | wave GEMV (`gl.sum` over K)     | scaled-WMMA (matrix core)         |
|--------------------------|---------------------------------|-----------------------------------|
| **route-owned** (a program per token-expert pair) | **R1** — direct wave GEMV per route | **R6** — duplicated-row scaled-WMMA per route |
| **output-owned** (a program per token, loops top-k)| **R5** — wave GEMV inside top-k loop | **R7 (this cell)** — scaled-WMMA inside top-k loop |

Read it as two moves from R1: going *down* a row buys you the single-store combine (no scatter buffer, no second reduction launch); going *right* a column swaps the vector reduction for the matrix core. R7 is R1 after both moves — equivalently, "R5 down the output-owned column, upgraded right to R6's engine."

## The trick that makes a GEMV fit a matrix instruction

The matrix core doesn't do vectors — it multiplies a 16-row tile. But decode only has one real activation row per route. R6's insight (inherited here): **broadcast that one row into all 16 fragment rows**, run the WMMA, and treat only row zero as semantic. In the code the broadcast is literally `+ duplicate_rows * 0` on the load offset, so every fragment row reads the same activation; the final store is masked to `matrix_rows == 0`. Fifteen rows are wasted arithmetic, but the matrix core is cheap enough at tiny-M that this can still beat a vector reduction — and correctness is unaffected because the extra rows never leave the register file.

## The top-k loop, in pseudo-code

```
program owns (token, n_tile):                # grid = M * ceil(N / BLOCK_N)
    acc = zeros[16, BLOCK_N] (fp32)          # only row 0 is real

    for slot in 0 .. TOP_K-1:                # statically unrolled
        expert = route_ids[token, slot] - EXPERT_START
        if expert not local: return

        route      = token * TOP_K + slot
        a_scale    = intermediate_scale[route]   # fp32, per-route
        w_scale    = routing_weights[token, slot] # fp32, per-route
        route_acc  = zeros[16, BLOCK_N] (fp32)

        for k0 in 0 .. K step 128:           # 128 = WMMA instruction K
            a = load activation row[route, k0:k0+128]   # E4M3, broadcast to 16 rows
            w = load packed W2[expert, k0:, n_tile]     # packed E2M1
            s = load W2 mx-scales[expert, k0:, n_tile]  # compact UE8M0
            route_acc = wmma_scaled(a, "e4m3", w, s, "e2m1", route_acc)  # <- matrix core

        route_acc *= a_scale                 # per-route FP32 intermediate scale
        route_acc += bias[expert]            # optional, FP32
        acc += w_scale * route_acc           # routing-weighted, FP32 running sum

    store row 0 of acc -> output[token, n_tile]   # exactly ONE final store
```

Contrast this with R5: identical structure, except R5's inner K loop is `route_acc += gl.sum(upcast(w) * a, axis=1)` — a vector reduction — where R7 issues a single `v_wmma_scale_f32_16x16x128_f8f6f4`. Everything outside the reduction (per-route scale, bias, routing-weight multiply, slot-ordered FP32 prefix, single masked store) is byte-for-byte the R5 sequence.

## Why it matters

The output-owned combine is the structurally clean part: no per-expert partial buffer in global memory, no scatter/gather, no second "combine" kernel, no atomics, no LDS staging. R5 already bought all of that. R7's bet is that you can keep every one of those properties *and* route the actual multiply-accumulate through the matrix core, which on gfx1250 is the throughput path for exactly this E4M3-by-packed-E2M1 shape. So R7 is the "have both" cell: matrix-core FLOPs and the tidy single-store dataflow, with no intermediate traffic reintroduced.

## Honest scope

This cell is **FFM correctness only — there is no timing here.** The claim R7 actually establishes is that the mechanism is *legal and numerically faithful*: across the full four-case matrix plus smoke, every route projection, weighted projection, slot prefix, and final row matched an independently compiled R5 within the frozen tolerance, and R7's own production vs. diagnostic outputs were **bitwise equal**. R7 and R5 are *not* bitwise equal to each other, and that is expected — a matrix core and a vector reduction round FP differently — but both land inside tolerance against the host reference. Making R7 self-consistent required disabling backend FP contraction (`enable_fp_fusion=False`); the fix pins the rounding boundary and is a correctness constraint for this harness, **not** a performance statement. Whether the 15 wasted fragment rows, register pressure, or the contraction knob pay off in cycles is left to timed cells (and R8's next-tile lookahead sits on top of, and is out of scope for, this one).

- Performance, register pressure, occupancy, cache traffic, and the cost/benefit of disabling outer FP contraction remain unknown because FFM timing is not meaningful and this cell performed no timing.
- Larger production dimensions, other N/warp layouts, K tails, remote-route skip semantics, end-to-end W1/W2 integration, and compiler versions outside the frozen source remain out of scope.

## Alternatives Considered

- Copying either CDNA4 donor verbatim was rejected because gfx1250's legal primitive, layouts, weight format, and rounding boundary differ.
- Importing the donors' next-tile register pipeline was rejected because R8 owns that independent schedule change.
- Importing split-K and `_moe_partial_reduce` was rejected because P2 is performance-only and would restore a partial buffer and second launch.
- Calling R5 in the public implementation was rejected because it retains the exact wave reduction R7 replaces; R5 is used only as the executable comparator.
- Reusing R6's route-major owner or adding all-row diagnostic output to production was rejected because R7 must retain R5 token ownership and one-store/no-partial-buffer boundary.
- Relaxing production-versus-diagnostic equality after the first full failure was rejected because it would hide a changed rounding boundary.
- Adding a production spill/capture store to block FP contraction was rejected because it would violate the one-store/no-intermediate-buffer contract. A target-specific inline-assembly multiply barrier was also rejected as less portable than the supported compiler option.
- Disabling FP contraction on only one entry was rejected because production and diagnostic would then intentionally compile different rounding semantics. Applying `enable_fp_fusion=False` to both entries is the narrow, symmetric boundary fix.

## Remaining blocker or next dependency

No R7 correctness blocker remains. R8 may independently evaluate next-tile register lookahead on top of this accepted output-owned scaled-WMMA mechanism; R7 itself makes no performance claim and does not authorize an R8 edit.
