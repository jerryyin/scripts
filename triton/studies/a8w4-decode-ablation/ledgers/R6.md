# R6 — Duplicate the decode row to fill a matrix tile, then throw the matrix core at it

## The idea in one breath

There is exactly one token to decode (M=1), so its projection is really a matrix-vector product — but instead of doing that reduction by hand with the vector unit, R6 copies that single row into all 16 rows of a matrix tile and runs the *matrix* engine (gfx1250's scaled WMMA), computing the same answer 16 times over and keeping only one copy.

## The picture

MoE decode is tiny-M: for each routed (token, expert) pair you compute one output row, `y = (x · scale) @ W_expert`. That is a GEMV — a vector against a matrix — with M=1. A matrix engine, though, wants a real tile: on gfx1250 the legal A8/W4 scaled instruction is `v_wmma_scale_f32_16x16x128_f8f6f4`, whose fragment is 16 rows tall. You have one row and the machine wants sixteen.

R6's move (borrowed from TokenSpeed's CDNA4 donor) is to *lie to the matrix engine*: broadcast the single real row into all 16 fragment rows, let the engine grind out 16 identical output rows, and store only row 0.

```
   R6: duplicated-row scaled WMMA (uses the matrix core)
   ------------------------------------------------------
   real decode row x[token]  (1 x K)
            |
            |  broadcast to all 16 rows  (stride 0 on the row axis)
            v
   +-----------------------------+        +-------------------+
   | x  x  x ... x   (row 0)     |        |  W_expert         |
   | x  x  x ... x   (row 1)     |        |  packed E2M1      |
   | x  x  x ... x   ...         |  @     |  16x16x128        |   -> 16x16 acc
   | x  x  x ... x   (row 15)    |        |  + UE8M0 scales   |
   +-----------------------------+        +-------------------+
   16 rows, all IDENTICAL                        |
            |                                    v
            |   acc *= activation_scale ; += bias
            v
   row 0 -> STORE   (mask: matrix_rows == 0)
   rows 1..15 -> computed, then DISCARDED   (15/16 of the work thrown away)


   R1 (k06): wave GEMV (no matrix core)
   ------------------------------------
   x[token] (1 x K)  *  W_expert  ->  elementwise products spread across
   the 32 lanes + per-lane registers, then  gl.sum(axis=1)  reduces K
   within the one wave.  No 16-row tile, no waste — a pure vector reduction.
```

The contrast is the whole point. R1 (the parent, `k06_route_direct_wave_gemv.py`) lays the K dimension across a wave's lanes and registers and collapses it with a vector `gl.sum`. R6 refuses to reduce by hand at all — it hands a deliberately wasteful, 15/16-redundant tile to the matrix core and lets the scaled-WMMA accumulator do the K reduction as a side effect of being a matrix multiply.

## The tension this ablation probes

Two ways to spend a decode's tiny FLOPs:

- **Vector GEMV (R1):** honest, no waste, but the vector ALU + `gl.sum` reduction is the only muscle doing work.
- **Duplicated-row matrix (R6):** 15 of every 16 rows are pure waste, but the muscle is the matrix core — which on these chips has enormous throughput relative to the vector path.

Nobody knows *a priori* which wins. A matrix engine so much faster than the vector unit can, in principle, come out ahead even while computing a tile that is 93.75% garbage — the redundant rows might be free if the engine would otherwise sit idle and the vector reduction is the true bottleneck. Or the wasted lanes and the register pressure of a full fragment might sink it. That crossover is exactly what a later timing study has to settle. R6 does **not** settle it: it answers only the prerequisite question — *is the duplicated-row scaled-matrix path even correct on gfx1250?* Because if the trick produces wrong numbers, there is no point timing it.

One honest wrinkle lives inside "is it correct." The donor was CDNA4 and used a scaled **MFMA**; gfx1250 has no such instruction. R6 is therefore a *mechanical substitution*: same idea (duplicate the row, run the matrix core, store row 0), different legal primitive (`gl.amd.cdna4.mfma_scaled` → `gl.amd.gfx1250.wmma_scaled` → `v_wmma_scale_f32_16x16x128_f8f6f4`). The registry filename still says "mfma" for historical/registry reasons — that is a label, not a claim about the emitted ISA, which is genuinely WMMA. (R7 pushes the same scaled-WMMA primitive further under output-owned top-k ownership.)

## Why anyone would try this

Matrix cores are where the throughput lives. On a decode step the arithmetic is trivial and the kernel is latency- and issue-bound, not FLOP-bound — so "wasting" 15/16 of a matrix tile costs almost nothing if those cycles were going to be spent anyway, and you get to reuse the one instruction the hardware is best at instead of an ALU reduction. If that bet pays off, the same duplicated-row path that already runs the big prefill GEMMs also handles decode, with no separate vector-GEMV code path to maintain. It looks wasteful on paper and can still win on the clock.

## What "correct" here actually established (and what it did not)

This ran under **FFM — the functional model — which has no notion of time.** Everything below is about *numbers*, never speed: all 16 duplicated rows come out **bitwise identical**; only row 0 is stored (exactly one semantic store, masked on `matrix_rows == 0`, no capture pointer in production); output matches both a host reference and the independently-compiled R1 kernel with zero observed error across the frozen cases; and there is no reduction (`gl.sum`/`tt.reduce`), no MFMA, no atomics, no LDS, no scratch — the reduction genuinely moved *into* the matrix instruction. What stays open is the whole point of the bet: **performance, register pressure, occupancy, cache traffic, and the GEMV-vs-duplicated-matrix crossover are all unknown**, because FFM cannot measure them. R6 clears the correctness gate and hands the timing question to a later AM/hardware run.
