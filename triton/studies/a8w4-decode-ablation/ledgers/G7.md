# G7 — Atomic route-weighted combine into token output

## The idea in one breath

Instead of each expert writing its partial result to a scratch buffer that a second pass sums, every expert program multiplies its W2 result by that route's gate and *atomically adds* it (in FP32) straight into the caller-zeroed token output row — so the top-k combine happens for free, inside the same kernel, as a side effect of the writes racing into one place.

## What problem this attacks

In MoE decode, one token is routed to `top_k` experts, and the model's answer for that token is the gate-weighted **sum** of what each expert produced. Somebody has to do that sum. The question G7 poses: who, and where?

The baseline (H0) answers "later, somewhere else." Each expert program is a self-contained tile: it computes its route's row, converts it to the output dtype, stages it through LDS, and scatters it out to a per-route slot in an intermediate buffer. Every route gets its own row. The actual cross-expert `+` is left undone — a separate reduction/scatter pass (think AITER-style `reduce.py`) has to read all `top_k` rows back and add them. Two global round-trips for the output: write the routes, then read-add-write the tokens.

G7 answers "now, here, by racing." There is no route-output buffer. The caller hands the kernel a token-shaped `[num_tokens, N]` FP32 buffer pre-zeroed to exact 0. Each expert program, at its epilogue, looks up which token its route belongs to and that route's FP32 gate, forms `gate * result`, and issues an atomic FP32 add into that token's row. The sum assembles itself in place.

## The combine, before and after

```
BEFORE (H0):  each expert stores its own row; a later pass sums them

  expert 0 (token 7, gate g0) --> [route-out buf, row A] --.
  expert 1 (token 7, gate g1) --> [route-out buf, row B] --|--> [ reduction ] --> token_out[7] = g0*r0 + g1*r1
  expert 3 (token 9, gate g2) --> [route-out buf, row C] --'      (pass 2)
                                    (intermediate buffer)          (extra global read + write)

AFTER (G7):   each expert adds directly into the token row; combine = the adds

  expert 0 (token 7)  weighted = g0*r0 --\
                                          >--  atomicAdd  -->  token_out[7]   (starts at 0)
  expert 1 (token 7)  weighted = g1*r1 --/                        ^
                                                                  |  both experts target the SAME row
  expert 3 (token 9)  weighted = g2*r2 ------ atomicAdd ----->  token_out[9]
```

### Why two experts hitting the same row is still correct

Experts 0 and 1 both own token 7 and both want `token_out[7] += weighted`. If they did a plain read-modify-write, they could interleave — read 0, read 0, add, add — and one contribution would be lost (a classic lost update). An **atomic** add makes each `+=` indivisible: the hardware serializes the two updates so the row ends at `0 + g0*r0 + g1*r1`, whichever expert lands first. The output row is the *running accumulator*, which is exactly why the caller must zero it first — and why each program's N-tile is disjoint, so races only ever happen on the summation axis (top_k), never on which columns get written.

## Baseline vs. this idea

| | H0 baseline | G7 |
|---|---|---|
| Per-expert epilogue | convert to out dtype -> LDS tile -> TDM scatter/store | FP32 `gate * result` -> `buffer_atomic_add` into token row |
| Intermediate route-output buffer | yes, one row per route | none |
| Cross-expert combine | separate reduction pass | the atomics themselves |
| Output ABI | `WriteBackIndx` / `writeback_size` (route slots) | `RouteTokenIndx` + FP32 `RouteGate` + `num_tokens`, caller-zeroed FP32 output |
| Output precision path | down-converted before store | stays FP32 through gate mul and accumulation |

Everything *before* the epilogue is untouched: expert grouping, gather/grouped input movement, scaled-WMMA, FP32 accumulation, bias, the whole K-loop. Only who-owns-the-output changed. In H0 a program emits one materialized row; in G7 all routes of a token contend on one FP32 row.

## Why it might matter

- **Deletes a buffer and a pass.** No route-output scratch to allocate, and no second launch to read `top_k` rows and add them. The combine stops being a distinct kernel.
- **Fewer global round-trips.** H0 writes routes then reads-adds-writes tokens. G7 writes once, straight to the destination.
- **Stays in FP32 the whole way.** No down-convert before the sum; the gate multiply and the accumulation are both FP32, so the numerical boundary is a clean FP32 reduction. Final cast to model dtype is the caller's job, outside this kernel.

## The cost and the risk (honest)

- **Atomic contention.** When many routes land on the same token row, their atomic adds serialize. At tiny-M decode this is bounded, but it is a real cost this idea trades against the saved pass — and G7 makes *no* speed claim (FFM has no timing).
- **Non-deterministic add order.** Atomics can land in any order, and FP add is not associative, so the bit pattern of a `top_k > 1` sum is not reproducible run to run. G7 treats this as an FP32 reduction contract, not bitwise equality: it checks the result against a worst-case rounding bound (`~2 * gamma(top_k) * sum|contribution|`) rather than an arbitrary tolerance. In the exercised cases the observed drift was at most ~2.4e-7, well under the derived bound (~3.2e-6).
- **FFM = correctness only.** Everything validated here is numerical: each route's weighted contribution matches reference, and the atomically-summed token output matches the reference sum within the order bound. The mandatory adversary — one token routed through two distinct experts, forced to collide on one row — passes. Whether atomics are actually *faster* than a reduction pass, and where the crossover is, is explicitly out of scope for this round.

## Parent → child ownership change

H0 and G7 both assign one expert-grouped ragged-M tile and one N tile to each program. `compute_pids`, `compute_offsets`, expert/slice metadata, X/W/scale descriptors, multibuffer TDM pipeline, scaled-WMMA formats and layout, FP32 accumulator, expert bias, activation position, and every K-loop decision are unchanged. No hunk changes input transport, grouping, scaled-WMMA math, bias, pre-epilogue numerics, scheduler, or dispatch policy.

H0 converts each route row to the model output dtype, stores it through an output LDS tile, then uses a TDM store or scatter to materialize that route row; a later consumer must combine the top-k route rows. G7 instead loads two grouped-route-aligned operands at the epilogue — `RouteTokenIndx[grouped_route]` (destination token) and `RouteGate[grouped_route]` (FP32) — computes `weighted_out = FP32(out) * FP32(route_gate)`, and calls `gl.amd.cdna4.buffer_atomic_add` on the caller-zeroed FP32 token accumulator. Programs for distinct experts may therefore share a token-output row, while each N tile remains disjoint. The kernel no longer converts to FP8, allocates output LDS, emits an output TDM descriptor, or stores a semantic route-output row. Final model-dtype conversion belongs to the caller. (Contrast R5, the separate output-owned combine: top-k looping and one final store, no atomics.)

## Accepted and rejected examples

Accepted: G7-A routes the two slots of one token through experts 0 and 1. The collision-free launch produced both expected weighted FP32 route rows exactly; the normal launch atomically combined them into FP32 `[1,256]` exactly.

Rejected: the host wrapper rejected BF16 output with `G7 output accumulator must be FP32` and rejected a nonzero FP32 accumulator with `G7 caller must zero-initialize the FP32 output accumulator`, both before launching the kernel. Shape, contiguity, routing-vector dtype/shape/contiguity, and token-index range are also explicit ABI boundaries.

## Alternatives Considered

- Output-owned top-k looping and one final store is intentionally not used: that is the separate R5 ownership change (output-owned combine without atomics).
- Direct route-owned wave GEMV is intentionally not used: that is the separate R1 family.
- Retaining a per-route scratch followed by an AITER-style reduction would preserve H0's materialization boundary and therefore would not test G7.
- BF16 atomics or pre-atomic output conversion would change the numerical boundary; G7 retains FP32 through gate multiplication and accumulation.

## Observed

- Exact child dispatch, FFM environment, pinned parent state, smoke, full matrix, 34 route contributions, five token sums, output contract rejections, and the generated-artifact proof all pass.
- Route-level kernel output matched the FP32 reference exactly in every case. Atomic reordering produced at most `2.3842e-7` absolute difference, below the independently derived worst-case bound `3.2427e-6`.
- Generated TTGIR/AMDGCN retain the grouped scaled-WMMA path and emit FP32 buffer atomics, with no output TDM scatter/store.
- No original target, shared harness, registry, other cell, compiler, Git state, build, or performance measurement was changed.

## Inferred

Because the generated kernel writes only the FP32 token accumulator and does not materialize route outputs, an integration using this ABI does not need an AITER-style separate top-k route-reduction launch or route-output scratch. That launch-level consequence is inferred because G7 does not modify or execute a production wrapper.

The numerical contract is nondeterministic in bit pattern for top-k greater than one but bounded as an FP32 reduction. The FFM issue order happened to differ by at most one or two FP32 ulps in the exercised collisions; hardware may choose another valid order within the stated bound.
