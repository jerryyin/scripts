# I1 — complete BF16-boundary wave-decode composition

## The idea in one breath

I1 is not a new trick — it is a composition/verification row: the first time the two halves of the route-direct wave-decode MoE are actually run together. Take the accepted R3 W1 stage (fused gate/up GEMV → SwiGLU → BF16 intermediate) and feed its output straight into the accepted R5 W2 stage (output-owned top-k weighted accumulate → one store per token), then check the complete decode is numerically correct end to end. The point of the cell is to prove the pieces *compose*, not to make anything faster.

## The full decode pipeline

```
                          LAUNCH 1  (R3 / k08, unchanged)
  X : [M, K] A8 (E4M3)  ┌───────────────────────────────────────────────┐
  x_scale : [M] FP32    │  W1: per (route, intermediate tile) owner       │
  packed gate/up W4  →  │    dequant W4 → FP32 gate GEMV + FP32 up GEMV    │
  route_ids             │    SwiGLU: SiLU(gate) * up   (all math in FP32)  │
                        │    round FP32 result → store BF16                │
                        └───────────────────────────────────────────────┘
                                          │
                       ┌──────────────────┴──────────────────┐
                       │  BF16 intermediate  [M*top_k, I]      │  ← the hand-off boundary
                       │  token-major, increasing-slot order   │     (R3 meets R5 here)
                       │  no value scale, no quant/dequant      │
                       └──────────────────┬──────────────────┘
                                          │
                          LAUNCH 2  (R5-derived, I1 owns)
                        ┌───────────────────────────────────────────────┐
  packed down W4     →  │  W2: per (token, output tile) owner             │
  down_scale            │    for slot in 0..top_k-1 (static unroll):      │
  routing_weights    →  │      load BF16 route row → FP32                 │
  route_ids             │      dequant W4 → FP32 down GEMV                │
                        │      + expert bias, * routing weight            │
                        │      acc += (FP32 prefix, increasing slot)      │
                        │    store token row ONCE                         │
                        └───────────────────────────────────────────────┘
                                          │
                          Y : [M, N] FP32   (one row per token)
```

Two explicit kernel launches, one global tensor between them. There is no fusion, no adapter kernel, no combine pass — just W1's output tensor handed by pointer to W2.

## Why an integration row has to exist at all

The ablation study's whole discipline is "one idea per cell." R3 proved the BF16 intermediate boundary in isolation; R5 proved output-owned top-k accumulation in isolation. Each was tested against its *own* synthetic inputs. That is exactly where interface bugs hide: "it works in pieces" says nothing about whether the bytes R3 actually emits are the bytes R5 actually expects — the dtype, the memory layout, the row ordering (token-major, increasing-slot), the absence of a scale factor. An isolated pass is a claim about a stubbed boundary; the real boundary is only exercised when the two stages share a tensor. I1's job is to make that boundary real and verify nothing falls through the crack.

The one thing that had to change to make them fit is small and localized: R5's W2 consumed an E4M3 intermediate plus a per-route FP32 scale (it loaded the row, then multiplied by `intermediate_scale`). R3 emits BF16, which is already a real value — no scale. So I1's W2 drops the scale pointer and the multiply and loads BF16 straight into the same FP32 reduction; every other line of R5 (expert lookup, packed-FP4 dequant, FP32 accumulate, bias, routing-weight multiply, increasing-slot prefix, single final store) is unchanged. The BF16 intermediate is *the* seam where R3 meets R5, and it is the only place I1 touches.

The verification is layered so a failure points at the seam: the integrated W1 output is checked **bitwise-equal** to a standalone R3 launch (so W1 is provably not perturbed by integration), and then W2 is driven from those exact R3 bytes and checked stage-by-stage — every route projection, weighted projection, running prefix, and the final token row. Adversarial controls (unequal routing weights, later top-k slots that must move the answer) keep the checks from passing vacuously.

## Sibling contrast: I1 vs I2

I1 and I2 are the same integration exercise with a different W1 boundary format. I1 wires R5's W2 onto the **R3 BF16** W1 path — the intermediate crossing global memory is BF16, wide and simple, no value scale. I2 does the same integration but onto the **R4 static-FP8** W1 path (the strict-A8 boundary), where the intermediate is FP8 plus a scale. That is why I1 is deliberately allowed to be the "no scale" variant and I2 owns the FP8-quantized composition — splitting them keeps each integration to one boundary format, preserving the one-idea-per-cell rule.

Honest scope: this is FFM, correctness only — no timing, no claim about which boundary is faster. I1 establishes that the BF16 two-launch decode is *correct*, a valid baseline for a later performance comparison against I2's FP8 boundary — but correctness alone says nothing about whether the extra BF16 traffic or the two-launch shape wins.

### Frozen stage and numerical contract

- W1 remains R3 exactly: E4M3 token input plus FP32 token scale; packed E2M1/UE8M0 gate/up weights; direct `(route, intermediate tile)` ownership; FP32 gate, up, bias, SiLU, and activated product; one BF16 `[M*top_k,I]` route-row output.

- W2 preserves R5 ownership: each program owns `(token, output tile)`, statically loops slots `0..top_k-1`, streams the selected expert's packed E2M1/UE8M0 down weight, computes one FP32 route projection, adds FP32 expert bias, multiplies by the FP32 route weight, updates the FP32 prefix in increasing-slot order, and performs one final FP32 token-row store.
- Diagnostic capture specializes a separate W2 entry and exposes every FP32 route projection, weighted projection, and after-slot prefix. Production has no capture pointers/buffers and exactly one semantic output store.
- The W1 CPU reference checks gate, up, activation, and BF16 output numerically. The integrated W1 boundary is bitwise-equal to a standalone accepted-R3 launch, and its production and capture variants are bitwise-equal.
- The isolated W2 CPU reference consumes those exact accepted-R3 BF16 bytes and checks every route projection, weighted projection, after-slot prefix, and final token output. A separate end-to-end CPU reference starts from the mathematical R3 BF16 boundary and checks the final output numerically.
- Numerical tolerance remains `maxtol=3e-2`, effective `rmstol=4e-3`.
