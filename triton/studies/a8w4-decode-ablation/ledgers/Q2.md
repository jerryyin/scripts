# Q2 — one-workgroup sigmoid + correction-bias top-k router

## The idea in one breath

Score each expert with a plain per-expert sigmoid, but pick the top-k using score-plus-a-per-expert bias — so the bias steers *which* experts win without ever touching the *weight* you emit, which is the bias-free sigmoid rounded to the router's storage dtype. This is DeepSeek-style biased gating (the bias is a load-balancing nudge on selection only), fused into one bounded decode workgroup on gfx1250.

## Why two different score notions at all

Naively you'd think a router computes one score and uses it for both "who gets picked" and "how much weight they get." Q2 deliberately splits those. The correction bias is a training/serving knob that rebalances *traffic* across experts (push an underused expert up, an overused one down) — but it is not a real measure of how relevant that expert is to the token. So the bias is allowed to change the routing decision, yet the gate coefficient that later multiplies the expert's output must stay honest: it's the raw `sigmoid(logit)`, with no bias baked in. Mixing the bias into the weight would silently rescale every expert's contribution by an arbitrary load-balancing offset.

## Worked example — the bias flip (the whole point)

Row of 8 logits, top_k=1, FP32, normalization off:

```
logits = [ 2.0, 0.0, -2.0, ... ]
bias   = [ 0.0, 0.5,  0.0, ... ]
```

Step 1 — sigmoid scores (bias-free): `sigmoid(2.0) = 0.8808`, `sigmoid(0.0) = 0.5`. Expert 0 is the stronger expert on its own.

Step 2 — add bias, but *only to decide the winner*: expert 0 → `0.8808 + 0.0 = 0.8808`; expert 1 → `0.5 + 0.5 = 1.0`. Now expert **1** wins. The bias flipped the choice.

Step 3 — emit the gate from the *un-biased* score of the chosen expert: weight = `sigmoid(0.0) = 0.5`. Not `1.0` (its biased choice score), not `0.8808` (the runner-up). The observed kernel output is exactly `id=1, weight=0.5`, while an un-biased top-1 control still picks `id=0`.

Contrast this against a Q1-style softmax router on the same row: softmax has no bias term, so it would keep expert 0 as the winner. The bias is precisely what makes Q2 diverge from Q1 here.

## Worked example — the dtype boundary (the second subtlety)

The sigmoid score is rounded to the *router's* storage dtype **before** it is used for selection, so rounding can reorder near-ties. BF16 row, first two experts:

```
logits = [ 0.0, 0.001, ... ]   (bias all zero)
```

In FP32, `sigmoid(0.001) > sigmoid(0.0)`, so expert 1 would edge out expert 0. But rounded to BF16, `sigmoid(0.001)` and `sigmoid(0.0)` collapse to the *same* value — now it's an exact tie, and the tie-break rule (smaller expert ID wins) selects expert 0 first. The kernel produced row-0 IDs `[3,4,0,1]`, whereas an otherwise identical unrounded-FP32 selection gave `[3,4,1,0]`. Same inputs, order swapped, entirely because the rounding happens on the selection side. The emitted gate is likewise the router-dtype-rounded sigmoid, so the weight boundary matches what a downstream A8W4 GEMM would actually see.

## Q1 vs Q2 at a glance

| Aspect | Q1 (softmax) | Q2 (sigmoid + bias) |
|---|---|---|
| Selection rule | top-k of row-softmax probabilities | top-k of `sigmoid(logit) + per-expert bias` |
| Weight source | the selected softmax probability | the selected **un-biased** `sigmoid(logit)`, rounded to router dtype |
| Bias in the weight? | n/a (no bias) | never — bias affects selection only |
| Normalization | divide top-k by their sum, then `× scale` | if on: re-round gates → divide by sum → `× scale`; if off: raw rounded gates, **scale ignored** |

Note the asymmetry in the last row: Q2 applies `routed_scaling_factor` *only* when normalization is on. With normalization off, the bias-flip case kept its gate at `0.5` and the BF16 case kept raw rounded sigmoids even though scale `2.827` was passed — the source contract deliberately drops the scale in that branch. Q1 always multiplies by the scale. This is a real donor quirk faithfully reproduced, not a cleanup opportunity.

## Why it matters

This is the exact gating math of DeepSeek-style MoE, where the auxiliary-loss-free load balancer is a bias added to the affinity for *routing* while the gate coefficient stays the pure sigmoid affinity. Getting the boundary wrong — leaking bias into the weight, or skipping the router-dtype round — would numerically corrupt every routed token's contribution and shift which experts fire on tie-adjacent inputs, and neither error would necessarily crash; it would just quietly produce a different (wrong) model. That is why the dtype boundary here is treated as correctness-critical, not a rounding nicety.

## Numerical and ordering contract

Load rank-2 `float16`, `bfloat16`, or `float32` logits at their stored dtype and cast to FP32; compute sigmoid in FP32; round every sigmoid score to the input router dtype before bias addition, selection, and gate extraction; add correction bias in FP32 only for selection; select biased choices in descending order, resolving exact ties to the smaller expert ID; emit the selected un-biased, router-dtype-rounded sigmoid gates as FP32. When normalization is enabled, re-round the selected gates to the router dtype, sum and normalize with the donor's zero-denominator guard, and multiply by `routed_scaling_factor`. When normalization is disabled, preserve the donor's exact asymmetric behavior: emit the unnormalized un-biased rounded gates and do not apply `routed_scaling_factor`. IDs must match exactly. Weights use the donor test's `atol=5e-3`, `rtol=5e-3` boundary.

The numerical boundary chain is: source dtype (`{float16,bfloat16,float32}`, loaded at stored dtype) → FP32 sigmoid → router-dtype score rounding → FP32 correction-bias addition for choice only → router-dtype gate rounding before optional normalization → FP32 output stores. Weights (gates) carry the `atol=5e-3,rtol=5e-3` boundary.

- Accepted shape/dtype bounds inherited from the donor: rank 2; router dtype in `{float16,bfloat16,float32}`; `0 < top_k <= E <= 1024`; `M * top_k <= 128`; correction bias is rank 1 with exactly `E` elements.
