# R4 — static-FP8 strict-A8 route-intermediate boundary

## The idea in one breath

Take R2's fused gate/up GEMV, and at the very last step — instead of writing the FP32 SwiGLU result out — divide it by one fixed, caller-supplied scalar and cast it to an 8-bit E4M3FN float, so the intermediate handed to W2 is 8-bit and the whole decode pipeline stays "strict A8" (8-bit activations end to end).

## What actually changes

R2 (k07) computes, per output column, `activated = SiLU(gate) * up` in FP32 and stores that FP32 value. R4 (k09) keeps every one of those steps bit-for-bit — same one activation load, same two packed-FP4 weight upcasts, same FP32 accumulation, same FP32 SwiGLU — and only rewrites the final store. The entire kernel-level idea is two lines: load one scalar scale, then `(activated / scale) -> E4M3FN` and store one byte instead of four. There is no BF16 path (that is R3's job) and no per-group dynamic scaling (that is G8/MXFP8's job).

"Static scalar" is the whole point: the scale is *one* FP32 number for the *entire* `[M*top_k, N]` output tensor, supplied from outside the kernel. The kernel never computes it, never reduces to find a max, never writes a scale per row or per 32-element group. It just consumes the number it was handed. In AITER's convention that number is `max(abs(reference)) / 448`, chosen once so the largest value lands exactly at E4M3FN's finite max of 448.

## Worked numeric example

Say the FP32 SwiGLU result for one column is `activated = 3.1`, and the caller supplies `scale = 0.0121` (an actual R4 scale, from the k04 case; it comes from `max_abs / 448`).

- Normalize: `3.1 / 0.0121 ≈ 256.2`. This is now inside E4M3FN's range `[-448, 448]`.
- Cast to E4M3FN (4 exponent, 3 mantissa bits, round-to-nearest-even). Near 256 the representable step is 16, so `256.2` rounds to `256.0`. That single byte is what gets stored.
- The consumer recovers the value later as `byte.float() * scale = 256.0 * 0.0121 ≈ 3.098`. The `~0.002` gap is the quantization error the FP8 boundary introduces — small, and within AITER's `maxtol=0.4 / rmstol=0.04` normalized budget.

Emitted for this column: **1 byte** (the E4M3FN encoding of 256.0) plus the shared FP32 scale `0.0121` carried alongside the whole tensor.

**Contrast — dynamic per-group scale (what G8/MXFP8 does instead):** a dynamic scheme would look at *this element's* 32-wide neighborhood, find that group's own max, derive a *local* scale (e.g. a UE8M0 power-of-two), and store both the FP8 byte *and* that group's scale. Different groups get different scales, so a group with tiny values keeps its precision instead of being crushed by a global scale set by some far-away outlier. R4 deliberately does none of this: one scale, no per-group scale storage, no reduction. That is what makes it "static" and what keeps it a strict one-line change from R2.

## R2 / R3 / R4 intermediate-precision table

| Ablation | Boundary store dtype | Bytes/elem | Scale | Pipeline | Cost of the boundary |
|---|---|---:|---|---|---|
| R2 (k07) | FP32 | 4 | none | not strict-A8 (16/32-bit intermediate) | none — full precision, most bandwidth |
| R3 (k08) | BF16 | 2 | none | not strict-A8 (16-bit intermediate) | just truncate FP32→BF16, no scale needed |
| R4 (k09) | E4M3FN (static FP8) | 1 | one global FP32 scalar | **strict A8** (8-bit end to end) | half of BF16's bytes, but needs a correct scale |

R4 is the only one of the three whose intermediate feeding W2 is 8-bit, so it is the only one that keeps activations 8-bit across the *entire* decode pipeline. It does so at half the byte cost of R3's BF16 — but unlike BF16, which is a lossy-but-scale-free truncation, FP8 has too little dynamic range to hold arbitrary magnitudes, so it *requires* an external scale to first bring values into `[-448, 448]`.

## Why it matters, and the risk

Two reasons. **Bandwidth:** decode is tiny-M and memory-bound; the route intermediate is a real traffic term, and 1 byte/element is half of BF16 and a quarter of FP32. **Strict-A8 consistency:** if W2 consumes 8-bit activations, then the stage boundary that produces its input should also be 8-bit — otherwise you pay a widen/narrow round-trip and break the uniform-8-bit story the pipeline is built around. R4 makes the R2 kernel a drop-in producer for an 8-bit W2 consumer.

**The risk is the scale.** E4M3FN's range is only `[-448, 448]`, so the static scalar is doing all the work of mapping your real magnitudes into that window. Set it too small and large values saturate/clip (lost range); set it too big and everything crowds toward zero where FP8's mantissa is coarse (lost accuracy). BF16 (R3) has none of this fragility — it just rounds. A wrong static scale silently degrades every element. AITER sidesteps this by pinning the scale to `max_abs/448`, which puts the largest value exactly at the range edge; note there is no explicit clamp in the kernel, so correctness depends on that scale actually bounding the data.

## Honest scope

This cell was validated under **FFM, which is correctness-only — no timing.** The bandwidth argument above is *motivation*, not a measured result; occupancy, register pressure, and cache behavior are explicitly out of scope. What the ledger *does* nail down is exactness of the boundary: across smoke plus four full cases, every device E4M3FN byte matched an independent host reference (zero raw-byte mismatches), the supplied scale was preserved bit-for-bit, and the generated code contains exactly one RTNE FP32→E4M3FN conversion (`v_cvt_scalef32_pk8_fp8_f32`) feeding one `global_store_b8` — no clamp, no scale store, no dynamic/per-32 marker. Adversary checks confirm the FP8 cast really changes values (not a no-op) and the result is genuinely FP8, not the BF16-rounded R3 result. How a production system calibrates that external scale is a separate question R4 does not answer.
