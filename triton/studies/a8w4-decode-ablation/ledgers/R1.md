# R1 — Route-Direct A8W4 Wave GEMV (keystone of the R-series)

## The idea in one breath

At decode (M=1..4 tokens) the MoE projection isn't really a matrix-matrix multiply — it's a handful of matrix-*vector* products, one per (token, expert) route. R1 throws away the grouped-GEMM machinery entirely and instead hands each route to a single wave that streams only its chosen expert's weights and reduces K with a plain vector multiply + wave-wide sum, keeping the accumulator in registers.

## Why the whole R-series exists

Matrix cores (WMMA/MFMA) want a *filled* MxN tile. The baseline H0 is built around that: it pads the token dimension up to a full M tile (typically 16), groups tokens by expert so a tile's worth of work exists, stages X/W/scales through TDM descriptors into LDS, and issues scaled-WMMA to reduce K. That is the right shape for prefill or big batches.

At decode you have M=1. To feed a 16-wide matrix tile you pad 1 -> 16 and then throw away 15/16 of the compute. Every piece of the grouped pipeline — the histogram/sort to group tokens, the ragged block schedule, the padded M tile, the gather/scatter buffers, the LDS matrix staging — exists only to keep matrix cores busy, and at M=1 there is nothing to keep busy. It is overhead wrapped around a matrix-vector product.

The R-series is the alternative algorithm family (Cursor's "warp decode" blog + TokenSpeed's Gluon donors). R1 is its foundational fork: recognize that at M=1 the operation is a GEMV, so use the hardware's *vector* path — multiply and reduce across a wave, accumulate in registers — and delete everything that only existed to serve the matrix path. R2–R9 layer independent ideas on top (gate/up fusion, bf16/static-FP8 intermediates, top-k weighting/combine in R5, matrix primitives, etc.); R1 is the spine every later R cell hangs off of.

## BEFORE / AFTER

This is the parent H0 -> child R1 ownership change, both as picture and as mechanism.

```
H0  (grouped GEMM + WMMA)                 R1  (route-direct wave GEMV)
============================              ============================

tokens ──▶ sort/group by expert           route r ──▶ token = r // top_k
        ──▶ pad M: 1 ─▶ 16 (waste 15/16)             slot  = r %  top_k
        ──▶ ragged block schedule                    expert = route_ids[token,slot]
                                                             − expert_start
one program owns:                         one program owns:
   (expert block, PADDED M tile, N tile)     (route, N tile)
        │                                          │
        ▼                                          ▼
  TDM descriptors ─▶ LDS staging          direct global loads (no LDS):
    X tile │ W tile │ scale tile             this token's X row
        │                                     this expert's packed W rows
        ▼                                     this expert's UE8M0 scales
  scaled WMMA over K  ◀── matrix cores            │
    (MxN accumulator in LDS/regs)                 ▼
        │                                   K reduction as a WAVE GEMV:
        ▼                                     x[k] * w[k]  (elementwise, FP32)
  FP8-round epilogue                          gl.sum over K within the wave
        │                                     accumulator lives in REGISTERS
        ▼                                          │
  scatter routed row (FP8)                         ▼
                                            store ONE FP32 row for route r

matrix core fed a 16-wide tile           vector unit fed a 1-wide GEMV
to multiply a 1-row vector.              — the shape the hardware wants.
```

- Before: H0 maps one program ID through expert-grouped ragged block schedules to `(expert block, padded M tile, N tile)`, stages X/W/scales through TDM and LDS, uses scaled WMMA for the K reduction, and stores/scatters a routed row after FP8 output conversion.
- After: R1 maps one program directly to `(route, N tile)`, derives `token = route // top_k`, localizes the selected route ID, streams only that expert's packed weight bytes and UE8M0 scales, applies the explicit A8 activation scale around an elementwise FP32 multiply, reduces K with `gl.sum` within the owning wave, adds bias in FP32, and writes the route's unique FP32 row.
- Expert grouping, group histograms, ragged block schedules, padded M tiles, gather/scatter buffers, TDM, LDS matrix tiles, MFMA, and WMMA are absent after the fork. Global traffic is direct activation, selected-expert weight/scale, route-ID, optional bias, and one route-row output. The accumulator is register-resident; no global scratch or shared-memory matrix handoff is allowed.

The mapping to hold onto: **one (route, N tile) -> one wave -> one output row.** A route is a single (token, top-k slot) pair. The wave reads that route's expert directly, does the dot products for its N columns, and writes exactly one FP32 row. No tile is ever padded, because no matrix instruction ever asks for one.

## The "GEMM is really a GEMV" insight

A projection is `Y[M,N] = X[M,K] · W[K,N]`. Matrix cores accelerate this when M is large enough to fill the tile's M dimension. At decode M=1 (or up to 4), so each token's output is `y[N] = x[K] · W[K,N]` — a matrix-vector product. There is no second row to amortize the matrix instruction over. Padding M to 16 doesn't create work, it creates *waste*: the matrix core computes 16 rows and 15 are discarded. A wave GEMV computes exactly the one row you need, using the vector ALUs and a cross-lane reduction that the wave already has, and never touches LDS.

## What one R1 program does (pseudo-code of the idea)

```
program owns pid  ->  route  = pid // num_pid_n     # which (token, slot)
                      pid_n  = pid %  num_pid_n     # which N sub-tile

token  = route // top_k
slot   = route %  top_k
expert = route_ids[token, slot] - expert_start      # direct route -> expert
if expert not local: return                         # skip, no padding

a_scale = x_scale[token]                             # per-token FP32 A8 scale
acc[BLOCK_N] = 0.0                                   # register-resident

for k0 in range(0, K, BLOCK_K):                      # K streamed in tiles
    x   = load x[token, k0:k0+BLOCK_K]  (E4M3 -> FP32)
    x   = x * a_scale                                # apply the A8 scale
    wq  = load packed_weight[expert, k0/2 .., n_tile]   # E2M1 nibbles
    ws  = load weight_scale [expert, k0/32.., n_tile]   # UE8M0 group scales
    w   = scaled_upcast(wq, ws -> bf16)             # gfx1250 native FP4 upcast
    acc += gl.sum(w * x, axis=K)                     # GEMV: multiply + wave-sum

if bias: acc += bias[expert, n_tile]                 # FP32 bias
store out[route, n_tile] = acc                        # ONE FP32 row
```

Everything after "for k0" is the GEMV: elementwise `w * x` across the wave's lanes, then `gl.sum` collapses the K axis *within the wave* into the register accumulator. One wave owns one output column (`NUM_WARPS == BLOCK_N`), so the whole reduction is register + cross-lane — no shared memory, no global scratch.

## One atomic fork, not four edits

The registry one-liner lists four removals — no expert grouping, no M padding, no LDS matrix tile, no MFMA/WMMA. These are not independent micro-optimizations you could apply one at a time; they are one decision seen from four sides. Once you decide the K reduction is a wave GEMV instead of a matrix instruction: you no longer need a filled M tile (so no padding), you no longer need tokens grouped to fill that tile (so no grouping/sort), and you no longer need LDS to stage operands for the matrix unit (so no LDS matrix tile). Remove any one without the others and nothing runs. That is why R1 is the *keystone* — it's the single algorithmic fork the rest of the R-series builds on.

## Changed ABI (important, and deliberate)

R1 does **not** produce the final MoE output. Its output is `[M*top_k, N]` in **FP32** — one raw projection row per route, in token-major / top-k-slot order. It does *not* apply router (top-k) weights and does *not* combine the top-k slots back down to `[M, N]`. That deferral is intentional: R1 owns only the route-direct GEMV; the top-k combine is R5's job. This is a different contract from H0, whose reference is the grouped `matmul_torch` producing an FP8-rounded, already-scattered routed row. So R1's numerical reference is its own (dequant weights to bf16, activation to FP32, per-token scale, FP32 dot, FP32 bias) — not H0's.

## Still genuinely A8W4 (not silently A16W4)

The activation stays 8-bit: `x` is E4M3 and R1 applies the explicit per-token FP32 scale itself. The weight stays 4-bit packed: R1 uses gfx1250's native packed-FP4 `scaled_upcast` (E2M1 nibbles + compact UE8M0 group scales, group=32), which is why the generated code contains `v_cvt_scale_pk8_bf16_fp4` and *no* `v_wmma`/`v_mfma`. The TokenSpeed donor was A16W4; porting it unchanged would have quietly become A16W4, so R1 deliberately keeps the E4M3 input and rejects a bf16 activation.

## Honest constraints

- **BLOCK_K limited to {256, 512}.** This is not a perf choice — it's a hardware boundary. The native scaled-upcast requires four packed bytes per lane; `BLOCK_K=128` gives only two, tripping `ScaledUpcastToLLVM.cpp:94`'s `inputVals.size() % 4 == 0` assertion. So the wrapper rejects 128 up front. (`BLOCK_K` must also be a power of two, divisible by the 32-element MX group, and divide K exactly — the K reduction is unmasked.)
- **NUM_WARPS == BLOCK_N**, structurally: exactly one wave owns each output column, both legal at {4, 8}.
- **FFM = correctness only.** R1 passed smoke + full (4 cases) + repeated smoke under FFM with *exact* FP32 agreement (max abs / max rel / RMS rel error all 0.0), zero shared bytes, zero global scratch, and verified native upcast with no matrix instruction. But FFM has **no timing**: there is **no** claim that R1 is faster than the grouped H0, and **no** measurement of the grouped-vs-route-direct crossover. Those remain intentionally unknown until an architectural (timed) model runs.

- Scalar nibble/exponent decoding was rejected because gfx1250's pinned `scaled_upcast` API directly supports packed E2M1 plus compact raw UE8M0 scales and is the closer precision-matched mechanism.
- Retaining `BLOCK_K=128` through scalar decoding or compiler modification was rejected: either would introduce a second idea and erase the native gfx1250 scaled-upcast boundary this cell is meant to test.
- Gate/up reuse, BF16/static-FP8 intermediate emission, top-k weighting, and matrix primitives are not folded into R1 because R2–R8 own those independent ideas.

## Remaining blocker or next dependency

None for R1. The coordinator can review this completed cell and decide whether its route-direct family should feed later integration or performance work; this cell makes no timing claim.
